# Generated App Standards

> **Status:** Design anchor for post-`v3.0.0` generated-app quality work.
> Created from the consolidated Claude Suite and Codex Suite review of generated
> CRUD and Kafka router apps and the broader EdgeForge generated-app baseline.

This folder defines suite-level standards for EdgeForge-generated Spring Boot
applications. These docs are intentionally not stored under one generated app:
they apply to every future app generated by the Engine.

## Documents

- [Generated App Quality Gate v1](generated-app-quality-gate-v1.md)
  defines the minimum production-candidate checklist, gap taxonomy, and
  ownership split for generated apps.
- [Generated-App Event Delivery Design](generated-app-event-delivery-design.md)
  resolves cross-service Phase A: an evidence-based architecture review of
  reliable domain-event publication from generated apps. Selects transactional
  outbox + a generated polling publisher (at-least-once, per-aggregate ordering),
  answers the Phase-A manifest question with an additive optional
  `event_publications` section, rejects sync dual-write / table-CDC / XA / event
  sourcing with reasons, defers CDC to an optional gated adapter, and ranks the
  broader generated-app gap list. DESIGN rev-1 — awaiting maintainer gate.
- [Generated-App Staging-Handoff Run Semantics Design](generated-app-staging-handoff-run-semantics-design.md)
  roadmap M5a — production semantics for generated staging-table downstream-handoff
  Spring Batch jobs. v1 is **staging-only** (fails fast on mixed staging+file jobs)
  and ships **failed-run `resume`** (`replace` deferred, since a completed JobInstance
  cannot re-run): durable caller-supplied **`runId` as the sole identifying
  JobParameter** (`businessDate` non-identifying, frozen and compared by a
  run-identity tasklet), resume-safe restart by removing the destructive clear-on-start, and
  idempotency via an **Engine-generated `UNIQUE(run_id, dedup_key)` internal_schema
  migration** (never an author-DDL edit) + a profile-pinned atomic upsert reusing the
  event-delivery invariant (spike-pinned per profile). Additive opt-in
  `run_semantics` block (byte-identical when absent); effectively-once staging state
  **bounded by an immutable-source-during-run precondition**; exactly-once processing
  never claimed. Batch metadata is a versioned/fingerprinted package singleton;
  per-handoff schema ids use deterministic, persisted ordinal allocation. Handoff/table
  renames are precisely attributed but **unsupported end-to-end in v1**: additive-only
  apply refuses with zero package mutation until a separate destructive-migration +
  baseline-reconciliation protocol exists. **Rev-10 selects the coordinated pre-adopter cut to
  single-dialect manifest `2.0`; V2-E delivers package/raw-schema unknown-field parity, reviewed
  standalone-v1 conversion, deterministic provenance, and no `1.0` bridge. Studio V2-S and both
  paired-branch and post-merge V2-X checkpoints are complete. M5a-S1 now delivers the CRUD-only,
  closed `run_semantics` contract, DDL/mapping validation, same-entity mixed-output rejection, and
  interim generate/plan/apply refusal. **M5a-S2 is delivered:** it adds the run-identity
  contract, Flyway-owned package Batch metadata, bounded native restart from authoritative
  `FAILED`/`STOPPED` states, and the opted-in trigger/card request shape. Durable
  PostgreSQL metadata may retain a running state after process death, so v1 returns the actual
  repository state and requires owner verification before authorized classification; automatic
  multi-instance recovery waits for ownership fencing. S2 also owns the closed JSON trigger/body,
  per-job console-card shape, and pre-launch run-ID canonicality/effective-width checks. Boundary
  whitespace is rejected, never trimmed, and the exact accepted value is shared by Batch and staging
  so padded `CHAR(n)` equality cannot collapse two JobInstances onto one physical key. The effective
  maximum is the lesser of the physical width and Spring Batch's 2500-unit parameter limit, measured
  with Java UTF-16 length for H2 safety and PostgreSQL conservatism. A generic keyset/frozen-bound
  reader is not selected. **M5a-S3 is delivered:** deterministic retained per-handoff uniqueness
  migrations, PostgreSQL `ON CONFLICT`, H2 ensure-row/update/read conflict handling, and opt-in
  clear-on-start removal now make public generate/plan/additive-apply safe for valid contracts.
  **M5a-S4 is delivered:** the existing compatibility harness now emits per-handoff results, makes
  opted-in run-identity failures blocking, and preserves legacy warnings. The four-slice M5a
  implementation is complete; `staging-restart`, `staging-idempotency`, and `staging-mixed-reject`
  remain reserved for later M3 registration. DESIGN rev-15; current original-date
  authority is defined in [section 7.1a](generated-app-staging-handoff-run-semantics-design.md#71a-authoritative-original-request-rev-15).
  The [M5a-S2 build prompt](generated-app-staging-handoff-run-semantics-s2-build-prompt.md)
  is historical, not the current date-authority algorithm.
- [Generated-App OpenAPI Artifact Design](generated-app-openapi-artifact-design.md)
  proposes a deterministic `openapi.yaml` emitted into generated CRUD apps that
  have an entity-CRUD surface. Drift is prevented by extracting a shared
  `GeneratedCrudApiModel` — the endpoint plan **and** the Java schema/field plan
  — built once before both emit lanes and consumed by all three renderers
  (controller, DTO/entity, spec), plus route- and schema-codegen parity tests
  tying every `$ref` to a real emitted Java type. Scoped to the **entity-CRUD
  REST contract** (other generated HTTP surfaces are named as excluded);
  build-time, no springdoc, no new runtime dependency. A generated-app standard
  artifact.
- [Generated-App Agent Guardrails Design (M4)](generated-app-agent-guardrails-design.md)
  designs the enterprise coding-assistant guardrails for generated apps: cited
  current-state inventory, the adopter-owned root `AGENT-POLICY.md` seam earned
  via a two-check (lexical-reservation + resolved-containment) reserved-path guard
  across every mutation sink, `agent-context.md` additions (ownership map rendered
  from a declared-artifact registry, verification sequence, precedence), the
  **Studio Step-6 Legacy Notes** carry-through (Markdown notes only — not a generic
  artifact transport), Kafka agent-context parity, tool-stub semantics decided
  against an independently rendered canonical template, and the machine-vs-prose
  enforcement mapping. Carries an *evidence rule* — a guardrail must not source its
  evidence from the side it guards against — and a correction log of the three
  mechanics that broke it. DESIGN rev-5 — awaiting maintainer gate; build follows as
  its own PRs.

This is the current generated-app standards set. It is intentionally not the
final set:
- `entity-identity-role-review-design.md` is the implemented design anchor for
  manual and KA-assisted identity role review; the full identity smoke passed
  after Studio and KS follow-up fixes.
- `high-tps-entity-profile-design-v1.md` is still deferred and should be added
  under this folder before accumulator-field implementation begins.
- `downstream-handoff-execution-topology-design.md` is still deferred and
  should be added under `docs/edgecontracts/` before expanding EOD/file generation
  modes.
- `cross-service-integration-design.md` is a v1 directional anchor and will be
  updated as the integration model matures and open questions are resolved.
- A separate runtime hardening backlog file was not created in this PR; those
  items are folded into section E of the quality gate and PR 7 of the roadmap
  until they need their own design.

## Scope

These standards cover:

- entity identity and transaction/event persistence correctness
- contract purity between API DTOs, response wrappers, and persisted entities
- CRUD temporal type propagation and fixed-width handoff value formatting
- Kafka router publish/correlation correctness and runtime schema validation
- evidence-trail population for governed generated-app proof packages
- staging table and downstream handoff integrity
- server-owned timestamps and audit metadata
- batch/file handoff production readiness
- idempotency, transactional consistency, and error contracts
- observability, security hooks, secrets, and runtime hardening
- high-TPS readiness boundaries, including accumulator-field patterns

These docs do **not** implement generator changes. They are the design and
review baseline for the next Engine and Studio implementation prompts.
