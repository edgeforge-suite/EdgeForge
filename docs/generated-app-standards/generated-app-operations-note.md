# Generated-App Deployment / Operations Note

> **Scope:** operational guidance for apps generated by EdgeForge Engine.
> Generated apps are standalone Spring Boot applications and do not require
> EdgeForge, Studio, KS/KA, MCP, or TestBench at runtime.

## Runtime file locations

Generated file/XML runtime features use configurable base directories:

- `app.file-ingest.base-dir`
- `app.xml-ingest.base-dir`
- `app.xml-output.base-dir`

The generated defaults are isolated per app instance:

```text
${java.io.tmpdir}/edgeforge-<bounded-context>-${APP_INSTANCE_ID:${random.uuid}}/<surface>/
```

This default is safe for local/demo runs because co-located instances do not
share a bounded-context-only directory. It is **not** a production storage
contract.

For production pods or VMs:

- Point all file/XML base-dir properties at persistent mounted volumes.
- Do not rely on container `/tmp`; it is often ephemeral, size-limited, cleaned
  by the platform, or mounted read-only.
- Ensure the non-root runtime user in the generated Docker image can read/write
  the mounted paths.
- Use a stable `APP_INSTANCE_ID` only when you intentionally want repeatable
  per-instance subdirectories; otherwise set explicit base-dir properties.
- Do not mount the same inbound directory across unrelated tenants or apps
  unless an operator-owned delivery process guarantees isolation.

Example overrides:

```bash
APP_FILE_INGEST_BASE_DIR=/mnt/edgeforge/inbound/files \
APP_XML_INGEST_BASE_DIR=/mnt/edgeforge/inbound/xml \
APP_XML_OUTPUT_BASE_DIR=/mnt/edgeforge/outbound/xml \
java -jar app.jar
```

## Secrets and runtime configuration

Generated apps externalize deployment-specific configuration. Production
deployments should provide these through the platform secret/config mechanism,
not committed files:

- `SPRING_DATASOURCE_URL`
- `SPRING_DATASOURCE_USERNAME`
- `SPRING_DATASOURCE_PASSWORD`
- OAuth2/JWT issuer, JWK set, audience, and authority mapping values — **only
  relevant if a custom, non-shipped profile registers the internal dormant
  security emitter (P1-5); no shipped profile requires these.**
- SOAP/client endpoint URIs or any other downstream system endpoints declared by
  the generated app.
- File/XML base directories listed above.

For enterprise PostgreSQL target profiles, datasource credentials are
environment-required and have no generated `postgres` fallback. If
`SPRING_DATASOURCE_USERNAME` or `SPRING_DATASOURCE_PASSWORD` is not supplied, the
generated app fails fast during startup instead of silently using a default
credential. The legacy-compatible H2 profile remains a local/dev profile with
`sa` and an empty password.

Generated apps ship plain HTTP with no in-application authentication — no shipped
target profile enables it (P1-5). Place them behind a TLS-terminating,
**authenticated** gateway. A merely "trusted" internal network is **not** an
accepted substitute: with no authenticating hop, every caller that can route to
the port is unauthenticated. Running without a gateway is **development-only**
operation, outside the supported v5 envelope below.

**Supported v5 posture (P1-5):** a single trusted authorization domain behind an
authenticated gateway. Every authenticated caller is trusted equally for all data
the application exposes. **The application's port must be unreachable except
through that gateway** — a caller that reaches the application directly bypasses
this entire posture, because the application itself performs no authentication or
authorization. Multi-tenant, per-user, object-level, and row-level authorization
are **not supported** until adopter-owned application authorization is implemented
and adversarially tested. See the
[generated-app security posture design](generated-app-security-posture-design.md).

Generic CRUD endpoints are retained. Selected OpenAPI operations are not the
entire emitted API: review the actual HTTP method/path surface and expose only
explicitly approved operations through the authenticated TLS gateway. Unapproved
CRUD, demo and batch endpoints must remain inaccessible through it, and the
application port must remain inaccessible except through it. Authentication alone
does not restrict routes/methods or establish business/object/tenant/row
authorization. Engine does not configure this gateway policy or generate an
endpoint allowlist. Runtime-disabled demo handlers still have registered mappings.
See the [approved endpoint policy](../enterprise-readiness-roadmap.md#endpoint-boundary-maintainer-decision).

Affected integer transport parameters bind as Java `Long`, including declared
`format: int32`; signed 32-bit range enforcement is an Engine-owned post-v5
limitation. Adopters needing those bounds must validate before business,
persistence or downstream effects. This is not full OpenAPI validation or a waiver
of other security/release requirements.

Rate limiting is gateway-owned. Generated apps do not enforce an in-application
rate limit; configure the shared budget at the non-bypassable gateway rather than
an independent per-replica limit.

Generated Kafka apps expose only `/actuator/health` by default. To expose metrics
and Prometheus, set
`MANAGEMENT_ENDPOINTS_WEB_EXPOSURE_INCLUDE=health,metrics,prometheus`. Enable that
opt-in only when the application port is unreachable except through the
authenticated, TLS-terminating gateway above.
