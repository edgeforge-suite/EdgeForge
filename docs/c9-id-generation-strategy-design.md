# C9 ID Generation Strategy Design

> Design-first document for Phase 3 C9. No implementation is approved by this
> document alone; it defines the boundary for later reviewable Engine work.

## Problem

EdgeForge currently has one first-class automatic ID generation strategy:
server-generated UUID for string persistence IDs.

The current canonical model has:

```python
CanonicalField.is_id: bool
CanonicalField.server_generated_id: bool
```

The Java emitter interprets that today as:

- if a field is the ID, is a string, and `server_generated_id=True`, emit
  `@GeneratedValue(strategy = GenerationType.UUID)`
- if a field is the ID, is a string, and `server_generated_id=False`, treat it
  as caller-supplied and do not emit `@GeneratedValue`
- if a field is the ID and is numeric, there is no first-class automatic
  strategy for `IDENTITY` or `SEQUENCE`

That means a manifest with an integer or long persistence identity cannot ask
the generated app to use database-generated numeric IDs in a deterministic,
explicit way. The Engine may still generate a numeric ID column, but it does not
have a canonical strategy vocabulary that all layers understand.

This is a design gap, not a one-line emitter fix. The strategy decision affects
translation, canonical metadata, Java annotations, SQL/Flyway DDL, request DTO
ownership, validation, and future Studio authoring.

## Design Decisions

### C9 Boundary

A1 answers: **which field is the persistence identity?**

C9 answers: **how is that persistence identity value generated?**

These concerns compose but must not be conflated. C9 should apply only after A1
or the existing heuristic has selected the field with `is_id=True`.

Examples:

- `TransactionPosting.postingId` can be selected by A1 and generated as a UUID.
- `Loan.id` can be selected by heuristic and generated by database identity.
- `LedgerEntry.entryId` can be selected by A1 and generated from a named
  sequence.
- `ExternalPayment.paymentReference` can be selected by A1 and remain
  caller-supplied.

### Compatibility

Existing `schema_version: "1.0"` manifests must remain unchanged. If no ID
generation override is declared, the Engine must keep today's behavior:

- string server-generated ID -> UUID
- string request-owned ID -> caller-supplied
- numeric ID -> no automatic numeric strategy unless explicitly declared

This is the non-regression contract.

### Archetype Scope

C9 applies to CRUD persistence entities only. It does not apply to the
passthrough-router archetype, which is stateless and repository-free.

### Target Profile Scope

The first C9 implementation should target the currently supported Spring Boot
CRUD profiles only. PostgreSQL and H2 both support `IDENTITY`-style generated
columns, but sequence details can differ by database. Any strategy that is not
portable across supported target profiles must either:

- be emitted in a profile-aware way, or
- fail validation with a clear unsupported-profile message

Do not add Oracle or other new database profiles as part of C9.

## Strategy Vocabulary

The design vocabulary should be small and explicit.

| Strategy | Meaning | Phase 3 generation consequence |
|---|---|---|
| `uuid` | Engine/server generates a UUID value for a string ID | Existing `GenerationType.UUID` behavior |
| `caller_supplied` | Caller provides the persistence ID in the create request | No `@GeneratedValue`; request DTO may expose the ID |
| `db_identity` | Database generates a numeric ID with identity semantics | `GenerationType.IDENTITY`; SQL identity column where supported |
| `db_sequence` | Database generates a numeric ID from a named sequence | `GenerationType.SEQUENCE`; SQL sequence plus sequence generator |

Deferred strategy concepts:

| Strategy | Why deferred |
|---|---|
| `composite` | Requires composite key modeling, `@EmbeddedId` / `@IdClass`, route semantics, DTO mapping, and repository type changes |
| `custom_generator` | Requires profile-specific or application-specific generator code |
| `snowflake` / distributed numeric IDs | Requires runtime coordination and operational assumptions outside Phase 3 |
| `ulid` | Useful, but requires a separate type/format decision and is not needed to close the numeric ID gap |

## Recommended Manifest Extension

The first C9 implementation should add a small top-level optional override list,
separate from A1's `identity_overrides`.

Recommended manifest-v1.1-style syntax:

```yaml
id_generation_overrides:
  - entity: LedgerEntry
    strategy: db_sequence
    sequence_name: ledger_entry_seq
```

For a simple database identity:

```yaml
id_generation_overrides:
  - entity: Loan
    strategy: db_identity
```

For a caller-supplied ID:

```yaml
id_generation_overrides:
  - entity: ExternalPayment
    strategy: caller_supplied
```

Rationale for a separate top-level list:

- C9 can be declared for an entity even when A1 does not need an identity-field
  override.
- A1 remains focused on field selection.
- C9 remains focused on value generation.
- It avoids expanding `identity_overrides` into a mixed concern that is harder
  for Studio to present.
- It allows later per-strategy validation without changing the A1 contract.

Each entry should refer to the canonical entity name. The strategy applies to
that entity's selected `is_id=True` field.

The first implementation should include optional `field` as a validation guard,
not as a second identity selector:

```yaml
id_generation_overrides:
  - entity: Loan
    field: loanId
    strategy: db_identity
```

If `field` is present, it must match the persistence ID selected by A1 or the
fallback heuristic. If it does not match, translation must fail with a clear
deterministic error. If `field` is absent, the strategy applies to the selected
persistence ID. This keeps simple overrides clean while protecting against
copy/paste mistakes where a generation strategy is accidentally applied to the
wrong field.

## Canonical Model Contract

The later implementation should add an explicit strategy to canonical metadata,
not infer everything from `server_generated_id`.

Recommended bounded model:

```python
class IdGenerationStrategy(str, Enum):
    UUID = "uuid"
    CALLER_SUPPLIED = "caller_supplied"
    DB_IDENTITY = "db_identity"
    DB_SEQUENCE = "db_sequence"

class CanonicalField(BaseModel):
    ...
    server_generated_id: bool = True
    id_generation_strategy: Optional[IdGenerationStrategy] = None
    id_sequence_name: Optional[str] = None
```

Compatibility rule:

- `id_generation_strategy is None` means preserve current behavior.
- When an override is declared, set `id_generation_strategy` on the selected ID
  field.
- Keep `server_generated_id` during the transition because existing emitters and
  tests use it to distinguish server-generated from caller-supplied IDs.

Derived compatibility mapping:

| Field state | Effective strategy when explicit strategy is absent |
|---|---|
| string ID + `server_generated_id=True` | `uuid` |
| string ID + `server_generated_id=False` | `caller_supplied` |
| non-string ID + `server_generated_id=False` | `caller_supplied` |
| non-string ID + `server_generated_id=True` | current legacy behavior, no automatic strategy |

The implementation may later convert this into a computed helper, but the first
PR should avoid broad model refactors.

## Translation Contract

Expected later flow:

1. Load optional `id_generation_overrides` from the manifest.
2. Run A1 identity selection first, including `identity_overrides` if present.
3. For each CRUD entity with a generation override, find the selected
   `CanonicalField` where `is_id=True`.
4. If no selected ID exists, fail with a clear deterministic error.
5. If an optional guard field is declared and does not match the selected ID,
   fail with a clear deterministic error.
6. Validate strategy/type compatibility:
   - `uuid` requires a string ID
   - `caller_supplied` can apply to string or numeric IDs
   - `db_identity` requires a numeric ID
   - `db_sequence` requires a numeric ID and a non-empty `sequence_name`
7. Set canonical ID generation metadata on the selected field.
8. Preserve current behavior when no override is present.

For C9, "numeric ID" means a canonical integer/long Java type (`Integer`,
`Long`, `int`, or `long`). String/UUID IDs and all other field types are not
numeric for `db_identity` or `db_sequence` validation.

## Emitter Consequences

### Java Entity Emitter

For the selected `@Id` field:

- `uuid`: emit existing `@GeneratedValue(strategy = GenerationType.UUID)`
- `caller_supplied`: emit no `@GeneratedValue`
- `db_identity`: emit `@GeneratedValue(strategy = GenerationType.IDENTITY)`
- `db_sequence`: emit `@SequenceGenerator(...)` plus
  `@GeneratedValue(strategy = GenerationType.SEQUENCE, generator = "...")`

The emitter must not infer numeric generation strategy from field type alone.
No override means current behavior.

### SQL / Flyway Emitter

For the selected primary key column:

- `uuid`: preserve current string/VARCHAR behavior
- `caller_supplied`: preserve current column type behavior
- `db_identity`: emit the profile-specific identity column syntax below
- `db_sequence`: emit a sequence plus a numeric primary key column

The first implementation should commit to this profile-specific SQL syntax:

| Target profile database | `db_identity` column syntax | `db_sequence` sequence syntax |
|---|---|---|
| PostgreSQL | `<column> <numeric_type> GENERATED ALWAYS AS IDENTITY` | `CREATE SEQUENCE <sequence_name>;` plus a numeric primary key column |
| H2 | `<column> <numeric_type> AUTO_INCREMENT` | `CREATE SEQUENCE <sequence_name>;` plus a numeric primary key column |

Keep this profile-specific in SQL generation rather than pushing dialect syntax
into the manifest. If a later target profile cannot support a declared strategy,
translation or generation should fail with a clear unsupported-profile message.

### DTO / Service Ownership

Generation strategy affects create request ownership:

- `caller_supplied`: ID may remain in create request DTO and service mapping.
- `uuid`, `db_identity`, `db_sequence`: ID should be treated as server/database
  generated and should not be required from the create request.

If a manifest maps a generated ID from the create request:

- `uuid`: preserve today's tolerant behavior where possible and emit a clear
  warning first, unless the generated code would be invalid
- `db_identity` and `db_sequence`: fail validation; silently discarding a
  caller-provided numeric ID while the database generates a different value is a
  contract violation

In every emitter path, an explicit `id_generation_strategy` must win over
legacy `server_generated_id` inference. The implementation PR should include a
short code comment at that decision point so future contributors do not
accidentally reintroduce inference precedence.

## Interactions

### A1 Identity Overrides

A1 selects the field. C9 selects the generation strategy for that field. If both
are declared, A1 must run first.

Example:

```yaml
identity_overrides:
  - entity: LedgerEntry
    persistence_id: entryId

id_generation_overrides:
  - entity: LedgerEntry
    field: entryId
    strategy: db_sequence
    sequence_name: ledger_entry_seq
```

### Request-Owned ID Detection

Current request-owned ID detection determines `server_generated_id=False` when
the selected ID appears in a create request mapping. An explicit C9 strategy
should win over that inference, but the implementation must report conflicts
clearly.

Example conflict:

- create request maps `Loan.loanId`
- C9 declares `Loan` strategy `db_identity`

The Engine should not silently generate a DB identity ID while also requiring
the caller to provide that ID.

### Cross-Entity And Filtered Queries

C9 does not implement cross-entity query logic, read-model derivation, or
filtered list predicates. It may help by making identity fields more explicit,
but query semantics remain separate future work.

### Passthrough-Router

Passthrough-router has no persistence identity and no repository. C9 overrides
should be ignored or rejected for passthrough-router manifests based on review
feedback, but they must not affect passthrough output.

My leaning: ignore them for passthrough-router to match A1's "unaffected"
behavior, and document that they have no effect.

### Studio

Studio support is future work. If Studio begins manifest-v1.1 wizard additions
for identity or generation strategy, revisit Studio-native Save/Open Project as
a prerequisite or near-term companion so users do not lose these authoring
decisions between sessions.

## Generic Example

An e-commerce order system may model an `Order` with:

- `orderId` as the persistence identity
- `orderNumber` as a business reference shown to customers
- `customerId` as a foreign key

For a greenfield generated app, the persistence ID may be numeric and database
generated:

```yaml
identity_overrides:
  - entity: Order
    persistence_id: orderId

id_generation_overrides:
  - entity: Order
    field: orderId
    strategy: db_identity
```

The generated app would use `orderId` as `@Id` and emit identity-based numeric
generation for that field, while `orderNumber` and `customerId` remain regular
fields governed by other rules.

## Bounded Implementation Acceptance Criteria

The later C9 implementation PR is ready when it meets all of these:

1. Existing manifests without `id_generation_overrides` generate unchanged ID
   behavior.
2. `db_identity` can be declared for a numeric persistence ID and emits
   appropriate Java and SQL for supported target profiles.
3. `db_sequence` can be declared for a numeric persistence ID with a required
   `sequence_name` and emits appropriate Java and SQL for supported target
   profiles.
4. `caller_supplied` can be declared and suppresses `@GeneratedValue`.
5. `uuid` preserves current UUID behavior and rejects non-string IDs.
6. Invalid strategy/type combinations fail with clear deterministic errors.
7. Duplicate generation override entries for the same entity are rejected at
   manifest validation time.
8. Optional `field` guards must match the selected persistence ID or fail
   clearly.
9. Passthrough-router output remains unaffected.
10. Manifest schema/docs describe the optional extension without changing
    `schema_version: "1.0"` compatibility.

## Explicitly Out Of Scope

- composite primary keys
- Oracle or any new database target profile
- distributed ID generators such as Snowflake
- ULID generation
- cross-entity query generation
- filtered pagination predicates
- business-key unique constraints
- service-level idempotency behavior
- Studio wizard UI for ID strategy
