# Regenerate / Maintain-Over-Time Model — Design

> **Status:** Design / docs only — no code in this PR. Addresses the **two MUST findings**
> from the suite blind-spot review ([`docs/suite-blind-spot-review-2026-06-14.md`](suite-blind-spot-review-2026-06-14.md)):
> regeneration (1) rewrites Flyway `CREATE TABLE` migrations and breaks already-deployed
> databases, and (2) unconditionally overwrites the service/domain layer that teams are
> told to extend. Both are the same problem: **EdgeForge generates fresh every run; it is
> not aware that it is *evolving an existing app*.**
>
> **Goal.** When a team regenerates from an *evolved, additive* manifest (a new
> entity / field / rule / downstream), EdgeForge should emit the **next version** safely:
> preserve developer-authored business logic, and evolve a live schema with **additive
> delta migrations** — never clobber hand-written code, never break a deployed DB.
>
> **Last updated:** 2026-06-14. Engine-standalone (B-group) track from the review; the
> Engine-internal mechanics here do not depend on the multi-session track.
>
> **Suite layer.** This is the **Engine-internal** half. The cross-repo **Change Plan
> contract**, Studio/KA roles, plan-hash binding, and sequencing vs the multi-session track
> live in [`docs/regenerate-maintain-suite-design.md`](regenerate-maintain-suite-design.md).
>
> **Reconciles:** [`docs/decisions/ADR-0004-deterministic-generation.md`](decisions/ADR-0004-deterministic-generation.md)
> (byte-identical regeneration) — see §3. **Complements** the Studio-side *Post-Generation
> Evolution Mode* (Gap 5 / the workspace decision-ledger): that thread produces an updated
> *manifest revision*; **this design is the missing Engine-side half** — consuming an
> evolved manifest to emit the next app version safely. **Bounded to additive change**;
> destructive change (drop / rename / type-narrow) is flagged for human review, never
> auto-applied.

---

## 1. Problem (grounded)

Today generation is a pure function of the manifest that **overwrites everything and reads
almost nothing** from the existing output:

- **Code (MUST-2).** Every Java class is written with an unconditional `path.write_text`
  (`java_emitter.py:781` `_write_java_file`; `engine.py:299` `_write_file_map`) — no
  skip-if-exists, no merge, no developer-owned files. The generated README §9
  (`build_emitter.py:765-788`) tells teams the **canonical core is `service/` + `domain/`**
  and to "add business logic there" — yet that is exactly the layer regeneration clobbers.
  The services are **not thin**: `_render_service` (`java_emitter.py:3292-4227`) emits real
  CRUD bodies, inlined entity↔DTO mapping, `applyBusinessRules` (`:4108`), cross-entity
  checks, and even `// TODO` "developer must fill in" placeholders (format validation
  `:4155`, string comparison `:4211`, computed-read `:3917`) — living inside a file that is
  destroyed on the next regenerate.
- **Database (MUST-1).** `emit_sql_files` (`sql_emitter.py:28`) assigns Flyway versions
  **positionally** — `for index, entity in enumerate(ordered_entities, start=1)` →
  `V{index}__create_<entity>_table.sql` (`:46-47`) — and `_clear_generated_migrations`
  (`:81-92`) **deletes and rewrites every EdgeForge-generated create-table migration on
  every run**. Adding or reordering an entity renumbers every downstream `V{n}`, and
  rewriting an already-applied `V1` triggers a **Flyway checksum mismatch** (refuses to
  boot) on any deployed Postgres. There is no `ALTER`, no "next version," no schema delta.

**The single existing exception** is the strongest hint at the fix: `_clear_generated_migrations`
already reads the `"Generated by EdgeForge"` header (`_is_edgeforge_generated_migration`,
`sql_emitter.py:95-100`) to distinguish EdgeForge-owned files from hand-written ones before
touching them. That **header-as-ownership-marker** pattern, generalized, is the backbone of
this design.

---

## 2. The architectural shift — regeneration-aware generation

EdgeForge gains a **regeneration-aware mode**: on a run into a populated output package it
reads exactly **two explicit, committed artifacts** from that package and nothing else:

1. **Per-file ownership headers** — every emitted file declares `generated` (EdgeForge owns;
   overwrite freely) or `developer` (scaffolded once; never overwrite).
2. **A schema baseline** — the logical schema the last generation produced, used to compute
   additive migration deltas.

Mode is **auto-detected**: no baseline / empty output → *first generation* (the existing
flow, now also emitting ownership headers + the baseline — a one-time golden refresh, §3);
baseline present → *regeneration* (preserve + delta). Both artifacts
live **inside the generated package** — build-time only, committed with the app — so the
**standalone invariant is preserved** (no runtime dependency on EdgeForge, no external
state store).

## 3. Reconciling ADR-0004 (byte-identical regeneration) — the load-bearing decision

ADR-0004 (Accepted) requires "the same manifest produces the same generated app —
byte-identical regeneration," which the golden-contract tests rely on. An incremental model
makes output depend on prior state, which naively breaks that.

**Resolution: redefine determinism as a pure function of `(manifest + committed baseline +
the contents of preserved developer-owned files)` — where the baseline and ownership headers
are *explicit, reviewable, in-package inputs*, not hidden history. "Byte-identical" means
*reproducible* (identical inputs → identical bytes), not "identical to pre-feature output."**

- **First generation now emits ownership headers + `schema-baseline.json`, so its bytes differ
  from today's** (an added header line per file + the baseline file). This is a **one-time,
  intentional golden refresh**: the golden-contract fixtures are updated in the PR that
  introduces headers/baseline (P1/P2). First-gen stays a pure, deterministic function of the
  manifest — byte-identical to the *new* goldens, run-to-run. (Do **not** claim first-gen is
  unchanged vs. the old output — it isn't, and that's expected.)
- **Regeneration** is byte-identical given the *same* `(manifest, baseline, preserved
  developer-file contents)`. The preserved developer files are a genuine input: the base is
  regenerated, the subclass is kept verbatim, so two regenerations over the same preserved
  files produce identical output. Golden tests gain a regeneration tier: fixture baseline +
  fixture developer files + evolved manifest → a deterministic, asserted delta (new `ALTER`
  migration, refreshed `…ServiceBase`, untouched developer files).
- The baseline + headers are committed and show up in the PR diff — regeneration is
  **reproducible and reviewable**, not "stateful magic," satisfying ADR-0004's intent under
  the new definition.

ADR-0004 must be amended with this clarification **in the PR that first changes generated
output** (P1/P2) — not deferred — because that PR is what intentionally breaks the old
byte-for-byte goldens (see §9).

## 4. Pillar A — the developer-owned layer (MUST-2)

### 4.1 Options

| Option | What | Trade-off |
|---|---|---|
| **A. Generation-gap (generated base + developer subclass)** ✅ | Emit an always-overwritten generated **base** (`{Entity}ServiceBase`) + a scaffold-once, never-overwritten **`{Entity}Service extends …Base`** where developers add logic via overridable hooks. | Deterministic; clean separation; new generated capability flows through the regenerated base; needs a one-time skip-if-exists check + designed hook seams. **Matches the maintainer's "developer version domain files" intent.** |
| B. Protected regions / markers | Generated files carry `// BEGIN/END USER CODE` regions the Engine re-injects on regen. | Engine must parse + merge its own output (stateful, fragile, marker drift); industry has largely abandoned this. |
| C. Skip-if-exists only (no base) | Emit service/domain only if absent; never overwrite. | Once emitted, the file is frozen — new entities/fields/rules never flow in. Fails "regenerate the next version." |
| D. 3-way merge | Store last-gen, merge against current. | Requires last-gen state + conflict resolution; heavy; overkill. |

**Recommendation: A (generation-gap)**, with a thin **file-ownership model** underneath.

### 4.2 File-ownership model (the foundation, reused by both pillars)

Extend the one existing per-file metadata sink — `render_generated_file_header`
(`audit.py:6-33`) — with an **ownership line** (`EdgeForge-ownership: generated|developer`),
and route **every** emitted file through **one central ownership-aware writer**,
`write_generated_file(path, content, ownership)`, that stamps the header and enforces the
overwrite policy:

- `generated` → always overwrite (today's behavior). Header: *"DO NOT EDIT — regenerated."*
- `developer` → **write only if absent** (scaffold once); on regen, **never overwritten**.
  Header: *"Safe to edit — preserved across regeneration."*

**This must be a single abstraction, not a two-helper patch.** Patching only `_write_java_file`
(`java_emitter.py:781`) + `_write_file_map` (`engine.py:299`) misses the many emitters that
write directly, which would make `developer` preservation and `generated` pruning partial and
surprising. All of these direct-write sites must be migrated to the central writer (or each
explicitly declared out of the protected scope):

- build files — `build_emitter.py:41-99`, `:116-175`
- audit / security configs — `audit_emitter.py:26-28`, `security_emitter.py:26-28`
- demo UI — `ui_emitter.py:184-186`
- passthrough helper — `passthrough_helpers.py:29-31`
- SQL migrations — `sql_emitter.py:47-75` (already the one ownership-aware path)
- SOAP resource copies / bytes — `java_emitter.py:8975-8994`

This generalizes the proven `_clear_generated_migrations` header-as-marker precedent
(`sql_emitter.py:95-100`) from SQL to **all** emitted files, through one writer.

### 4.3 The service seam (where the meaningful logic + `// TODO`s live)

Per entity, replace the single overwritten `{Entity}Service.java` with:

- **`{Entity}ServiceBase.java`** — `generated`, `abstract`, always overwritten. Holds the
  generated CRUD bodies, inlined mapping, and cross-entity checks (today's `_render_service`
  content). `applyBusinessRules` becomes **`protected`** (it is `private` today,
  `java_emitter.py:4108-4109`) so the subclass can extend it.
- **`{Entity}Service.java extends {Entity}ServiceBase`** — `developer`, **scaffolded once,
  never overwritten**. Carries `@Service` (the concrete Spring bean), a pass-through
  constructor, and stubbed `@Override`s for the hooks. **This is the developer's file.**
- Controller wiring is unchanged (`_render_controller` injects `{Entity}Service` at
  `java_emitter.py:2010,2053-2056`; the concrete subclass is the bean). Cross-entity
  repositories (`:3424-3441`) move into the base constructor and are passed through by the
  subclass's `super(...)`.

**Concrete hook API (the first supported set — explicit, not "the TODOs become hooks"):** the
base declares these `protected` extension points with safe defaults; the scaffolded subclass
gets stubbed `@Override`s:

- `beforeCreate({Entity})` / `afterCreate` / `beforeUpdate` / `afterUpdate` / `beforeDelete(id)`
  — lifecycle hooks; default no-op.
- `applyBusinessRules({Entity})` — default runs the generated rule checks; override to extend.
- `validateFormat({Entity}, field, value)` — the format-validation TODO (`:4155`); default no-op.
- `compareValues(...)` / `validateComparison(...)` — the string-comparison TODO (`:4211`); default no-op.
- `computeDerivedRead(...)` — the computed-read TODO (`:3917`); default
  `throw new UnsupportedOperationException("Override computeDerivedRead in {Entity}Service")`.

**New-hook notification (the scaffold-once gap):** because the subclass is scaffolded once, a
hook *added later* to the regenerated base will **not** auto-appear as an override in an
existing subclass. Mitigation: (a) every new hook ships a **safe default** in the base (no-op,
or a clearly-messaged `UnsupportedOperationException` for must-implement ones) so old
subclasses still compile and run; (b) the generated `agent-context.md` / README emits a
**"hooks available to override"** list per entity, refreshed each regen; (c) the regen summary
**logs newly-added hooks** so a developer knows to wire them.

Result: regeneration refreshes `…ServiceBase` (new entities/fields/rules flow in) while the
developer's `{Entity}Service` survives untouched and still compiles.

> **Alternative if the hook surface grows wide:** instead of base/subclass, emit a
> fully-generated `{Entity}Service` plus a scaffold-once `{Entity}Hooks` / `{Entity}Customization`
> bean it injects and calls. That keeps the generated service authoritative and the developer
> surface a single injected bean. Recommended fallback if the base's `protected` surface
> becomes unwieldy; the base/subclass split is the MVP default.

### 4.4 Other layers

- **Entity / `domain/`** — shape is the manifest's source of truth, so it stays `generated`.
  Entity *behavior* belongs in the service hooks (MVP). An optional developer domain-service
  can be added later if demand appears (§9, future).
- **Repository** — today an empty `JpaRepository` marker (`java_emitter.py:1678`). **Keep it
  `generated` for MVP** (do **not** scaffold-once). Scaffold-once would preserve hand-added
  queries but **block** any future generated repository methods, and the repository is empty
  today so there is nothing yet to preserve. **Explicitly out of scope for MVP:** preserving
  developer-added repository queries — deferred to a later **repository seam** (a generated
  `{Entity}RepositoryBase` interface + a `developer` `{Entity}Repository`, or a developer-owned
  Spring Data **fragment**). Until then, custom queries belong in the `developer` service layer.
- **Controllers, DTOs, adapters, config, exceptions** — stay `generated` (preserved-edge
  contract surface; the README already says "do not change" these).

### 4.5 Regeneration-aware cleanup (orphaned generated files)

Today only SQL migrations are pruned; stale Java from a renamed/removed entity lingers
(agent-confirmed). Extend ownership-aware pruning to all `generated` files: on regen, remove
orphaned `generated`-owned files no longer in the manifest, but **never** touch
`developer`-owned files. (Reuses the header-marker read; same safety as
`_clear_generated_migrations`.)

### 4.6 Legacy-package adoption (existing apps with no ownership line / no baseline)

Apps generated before this feature carry the `"Generated by EdgeForge"` header
(`audit.py:18-31`) but **no ownership line and no `schema-baseline.json`**. Regenerating into
such a package must not silently clobber developer work. One-time **adoption** policy:

- **Classify:** a file with the EdgeForge header but no ownership line defaults to
  `generated`; the new `developer` files (e.g. `{Entity}Service`) are **scaffolded going
  forward** only if absent.
- **Protect hand-edited legacy generated files:** before overwriting a legacy `generated`
  file, detect divergence (it does not match what regeneration would produce) and
  **warn + back up (`.bak`) or fail closed** — never silently overwrite a hand-edited
  generated file (mirrors the §10 guard).
- **Seed the baseline:** the adoption pass writes `schema-baseline.json` from the current
  manifest (and stamps ownership headers), so the *next* regen has a baseline to diff against.

This makes the rollout safe for the existing fleet, not just greenfield apps.

## 5. Pillar B — incremental, additive DB evolution (MUST-1)

### 5.1 Options

| Option | What | Trade-off |
|---|---|---|
| **A. Baseline-diff additive deltas** ✅ | Record the emitted schema as a baseline in the package; on regen, diff additively and emit `V{next}__alter_*.sql`; treat applied `V1..Vk` as immutable. | Real "next version"; bounded to additive; needs a committed baseline + a diff step. Reconciles with ADR-0004 via §3. |
| B. Append-only, no diff | Never re-clear `V*`; append new `V{n+1}` for new content. | Can't handle "add a field to an existing entity" (that's a column delta, which needs a diff) — collapses into A. |
| C. Managed handoff / external diff (Liquibase/Flyway diff) | Emit desired schema; let a tool/team author the ALTER. | Punts the smarts; changes the generated stack; less "EdgeForge is smart enough." |
| D. Hibernate `hbm2ddl` auto-update | Let the ORM evolve the schema at runtime. | Not production-safe; violates the deterministic, migration-based posture. |

**Recommendation: A.** All schema info needed to diff additively is already in
`MetadataProject` / `CanonicalEntity` / `CanonicalField` (`metadata/models.py:259/134/107`)
— types, defaults, IDs, FKs, and a (derived) nullability predicate.

### 5.2 The baseline

At generation, write a deterministic **`db/schema-baseline.json`** (in-package, `generated`,
committed) capturing the **effective emitted SQL state** — not just raw field metadata, since
the DDL depends on target profile, audit toggle, ID strategy, UUID-FK width, and check
constraints (`sql_emitter.py:158-212,272-284,340-356`). Capture, per table:

- target **DB / profile** + whether **audit columns** were emitted (`emit_audit` toggle);
- columns: name, **emitted SQL type**, nullable, default, and **check constraints**;
- **PK / id-generation strategy / sequence** name;
- **FK names** + targets;
- **staging tables** (validated author DDL copied unchanged from
  `metadata.staging_table_ddls`, `sql_emitter.py:61-75`): a **checksum** of the
  decoded DDL string (the baseline does not persist the validated parser model);
- the **Flyway version high-water mark**.

It is an explicit, diffable input (§3), not hidden state.

### 5.3 The diff (additive only)

On regen (baseline present), diff new manifest-derived schema vs the baseline and emit, as
**new** `V{next}__alter_*.sql` files (never rewriting `V1..Vk`, never re-clearing them):

- **New entity** → `V{next}__create_<entity>_table.sql` (+ FK alters), appended.
- **New field on an existing entity** → `V{next}__alter_<entity>_add_<field>.sql` =
  `ALTER TABLE … ADD COLUMN …`.
- **New FK** → `ALTER TABLE … ADD CONSTRAINT …`.
- Indexes are **not modeled/emitted today** (agent-confirmed) → out of scope until indexing
  exists; no diff to compute.

Then update `schema-baseline.json` and bump the high-water mark.

### 5.4 The nullability rule (critical correctness point)

A column added to a **populated** table cannot be `NOT NULL` without a default. Nullability
today is a *derived* predicate (`_field_requires_persistence_constraint`,
`java_emitter.py:1533-1549`), not a raw flag. Rule for additive `ADD COLUMN`:

- Field is nullable, or `required`/`not_null` **with** a `default_value` → emit
  `ADD COLUMN … [DEFAULT …] [NOT NULL]` safely.
- Field is `required`/`not_null` **without** a default → **do not auto-emit an unsafe
  `NOT NULL`.** Flag it as needing a manual data-backfill migration (§5.5).

### 5.5 Destructive / unsafe changes — flagged, never auto-applied

**MVP auto-additive set (deliberately tiny):** only **new table**, **new nullable-or-defaulted
column**, and **new FK**. Everything else **fails closed** — a clear message + a stubbed,
commented manual-migration file for human authoring + review — until the baseline model proves
itself. Regulated / enterprise teams audit DB changes; these must never be silent.

Change-type matrix:

| Change | Class | Action |
|---|---|---|
| New table | additive | append `V{next}__create_*` (+ FK alters) |
| New nullable column / new column with default | additive | `ADD COLUMN …` |
| New required column **without** default | unsafe | fail closed + manual stub (needs backfill) |
| New FK constraint | additive | `ADD CONSTRAINT …` |
| New index *(once indexes are modeled — not today)* | additive (future) | `CREATE INDEX` |
| Drop column / drop table | destructive | fail closed |
| Rename column / table (reads as drop+add) | destructive | fail closed |
| Type change (narrow **or** widen) | unsafe | fail closed (review required) |
| Nullability tighten (`NULL`→`NOT NULL`) | unsafe | fail closed (backfill) |
| Default change | unsafe | fail closed |
| Check-constraint add / tighten / remove | unsafe | fail closed |
| `max_length` narrow (truncation) / widen | destructive / unsafe | fail closed |
| ID strategy / sequence change | unsafe | fail closed |
| Relationship (FK) target/source change · FK rename/removal | destructive | fail closed |
| Audit-profile toggle: columns **added** / **removed** | additive / destructive | add → `ADD COLUMN`; remove → fail closed |
| Staging DDL change (authoritative text; checksum-only, not semantically diffed) | unsafe | checksum mismatch → fail closed (no safe additive semantic diff) |

This bounds risk to a small, provable additive surface and matches the additive-only doctrine.

## 6. Unified flow

```
regenerate(manifest, output_package):
  if no schema-baseline + no ownership headers in package:   # first generation
      emit everything (generated); write baseline; write ownership headers   # deterministic; goldens refreshed once when headers+baseline land (§3)
  else:                                                       # regeneration-aware
      CODE:  refresh all `generated` files; SCAFFOLD `developer` files only if absent;
             prune orphaned `generated` files; never touch `developer` files
      DB:    diff manifest-schema vs baseline (additive only);
             append V{next}__alter_*.sql; keep V1..Vk immutable; update baseline;
             FAIL CLOSED on destructive/unsafe deltas with manual-migration guidance
```

Developer experience: edit the manifest (add entity/field/rule/downstream) → regenerate →
get new `ALTER` migrations + refreshed generated bases, with your `{Entity}Service` business
logic **intact**.

## 7. What this design is NOT

- **Not** destructive auto-migration (drop/rename/type-narrow/unsafe-NOT-NULL) — flagged for
  human review, never auto-applied.
- **Not** a 3-way code merge or protected-region parser — the generation-gap split avoids both.
- **Not** a manifest v2 / breaking change — manifest stays additive `1.0`-compatible.
- **Not** a change to the standalone nature of generated apps — baseline + ownership are
  build-time, in-package artifacts; zero runtime dependency on EdgeForge.
- **Not** runtime ORM schema auto-update (no Hibernate `hbm2ddl` in prod).
- **Not** the Studio authoring side — *Post-Generation Evolution Mode* (reopen / ingest BRD /
  produce the updated manifest revision) is the complement; this consumes its output.

## 8. Relationship to existing design

- **Post-Generation Evolution Mode (Studio/KS, Gap 5 + workspace decision-ledger):** produces
  an updated *manifest revision* (with `manifest_hash`), explicitly stops there, and disclaims
  branch/merge/Git semantics. **This doc is the Engine-side downstream half** — complementary,
  not contradictory.
- **ADR-0004 (byte-identical regeneration):** reconciled in §3 (determinism redefined over
  `manifest + committed baseline + preserved developer-file contents`); amend the ADR in the
  first output-changing PR (P1/P2), per §3 / §9.
- **Engine roadmap "prefer Engine fix + regeneration" doctrine:** this design *is* the
  evolution of that doctrine from "full rewrite" to "safe incremental regeneration."
- **Blind-spot review #235:** this is the design for its two MUST findings (the
  Engine-standalone B-group).
- **Multi-session track:** orthogonal; regeneration reads the *package's* baseline/ownership,
  independent of per-session output-dir placement.

## 10. Risks & open questions

- **ADR-0004 / golden tests (§3)** — the central reconciliation; must land with regen golden
  tests so the new determinism definition is enforced, not asserted.
- **Nullability of added columns (§5.4)** — the most error-prone correctness point; the
  derived predicate must be applied per the additive-ADD-COLUMN rule, not raw `not_null`.
- **Hook-seam design** — which extension points `{Entity}ServiceBase` exposes (the `// TODO`
  spots are the obvious first set); over-exposing hooks bloats the base, under-exposing forces
  developers back into generated files. Resolve in P1 with a small, named hook set.
- **Developer edits a `generated` file anyway** — header says DO NOT EDIT; regeneration
  overwrites. Document loudly; optionally a pre-regen check that warns on modified `generated`
  files.
- **Baseline drift / hand-edited migrations** — if a team hand-edits a `V*` or the baseline,
  the diff can mismatch. Mitigate: the baseline is `generated`-owned (don't hand-edit), and the
  diff fails closed on inconsistency rather than guessing.
- **Open question for the maintainer:** baseline location/format — `db/schema-baseline.json`
  in-package (recommended) vs reusing the Studio-side `manifest_revisions[].manifest_hash` as a
  cross-check. (Recommendation: in-package baseline is authoritative; the Studio hash is an
  optional provenance cross-check.)

## 11. Verification

- **First-gen determinism:** goldens are refreshed **once** when headers/baseline land (§3);
  thereafter first-gen is byte-identical run-to-run (reproducible, not identical to
  pre-feature output).
- **Code preservation:** generate → hand-edit `{Entity}Service` → regenerate from an evolved
  manifest → developer edits intact, `{Entity}ServiceBase` refreshed with the new
  entity/field/rule, controller still wired.
- **Additive DB delta:** generate (V1..Vn) → add a field + a new entity → regenerate → only
  new `V{next}__alter_*` / `__create_*` appear; `V1..Vn` byte-identical (no Flyway checksum
  break); applying both old + new on a seeded DB succeeds.
- **Destructive fail-closed:** drop/rename/type-narrow/unsafe-NOT-NULL in the manifest →
  regeneration fails with a clear message + a manual-migration stub; no silent DDL.
- **Determinism:** regenerate twice from the same `(manifest, baseline, preserved developer files)` → byte-identical.
