# A1 Identity Semantics Design

> Design-first document for Phase 3 A1. No implementation is approved by this
> document alone; it defines the boundary for later reviewable Engine work.

## Problem

EdgeForge currently selects a single persistence identity field through
`_select_entity_id_field_name()` in `appbuilder/metadata/translation.py`.
That heuristic works for simple system-of-record entities where one field is
clearly the entity ID:

- `Customer.customerId`
- `Account.accountId`

It is not enough for transaction, posting, event, and history-style models where
several fields look like identifiers but mean different things. For example, a
`TransactionPosting` could contain:

- `accountId` as a foreign key to the owning account
- `transactionId` as an upstream transaction or event identifier
- `postingId` as the persistence identity for the generated app
- `externalReference` as a business or provider reference
- `idempotencyKey` as a replay guard

If the heuristic picks the wrong field, the error propagates into generated
`@Id`, route parameters, `findById`, repository lookups, foreign keys, and
future query semantics.

This is a modeling gap, not a regex bug. The Engine needs an additive way for a
manifest author to say which field is the persistence identity while preserving
today's inference as the fallback.

## Design Decisions

### A1 Boundary

A1 answers: **which field is the persistence identity?**

C9 answers: **how is that identity value generated?**

These are separate concerns. A field can be the persistence identity and still
be server-generated UUID, client-supplied, or eventually generated by a numeric
database strategy. A1 must not introduce numeric IDENTITY, SEQUENCE, or other
generation strategies; those remain C9.

### Compatibility

Existing `schema_version: "1.0"` manifests remain unchanged. If no explicit
identity override is declared, `_select_entity_id_field_name()` must run exactly
as it does today.

The A1 implementation contract is:

1. Check for an explicit persistence identity override.
2. If present, select that field as the entity `@Id`.
3. If absent, run the current heuristic unchanged.

### Archetype Scope

A1 identity semantics apply to CRUD canonical entities only. They do not apply
to the passthrough-router archetype, which remains stateless and should not
inherit CRUD persistence identity behavior.

## Identity Vocabulary

The design vocabulary is broader than the first implementation. Only
`persistence_id` should affect Engine generation in the first bounded PR.

| Role | Meaning | Phase 3 generation consequence |
|---|---|---|
| Persistence identity | Field that becomes generated app persistence identity | Drives `CanonicalField.is_id`, `@Id`, route ID, `findById` |
| Business key | Domain-meaningful natural key, such as `invoiceNumber` or `orderNumber` | No Phase 3 generation change; future unique constraint candidate |
| Event ID | Upstream event or transaction identifier, such as `transactionId` | Regular field; must not become `@Id` solely by name |
| Foreign key | Reference to another entity, such as `accountId` on a posting | Continue using `cross-entity-exists`; future field-level FK metadata may complement it |
| Correlation ID | Cross-system tracing or workflow correlation identifier | Regular field in Phase 3 |
| Idempotency key | Replay guard used to make writes idempotent | Regular field in Phase 3; service-level idempotency is future work |
| Provider/external ID | Identifier assigned by an external provider | Regular field in Phase 3; may overlap with business key in later design |

## Recommended Manifest Extension

The first A1 implementation should add a small entity-level override rather than
a full field-role model.

Recommended manifest-v1.1-style syntax:

```yaml
identity_overrides:
  - entity: TransactionPosting
    persistence_id: postingId
```

`identity_overrides` should live at the top level of the manifest
`AppDefinition`, parallel to `data_handoffs`, `rules`, and
`legacy_references`. The implementation should add a small Pydantic model such
as `IdentityOverride(entity, persistence_id)` in `appbuilder/contracts/manifest.py`.

Rationale:

- it is additive and optional
- it avoids adding a full entity field declaration section to manifest-v1
- it mirrors the current single `is_id` persistence identity model
- it lets the author correct multi-identifier entities without changing all
  field metadata
- it leaves room for later role metadata if `business_key`, `event_id`, or
  `idempotency_key` need first-class generation behavior
- it also handles the no-candidate case where an entity has no `*Id`-named
  fields but the manifest author can still identify the persistence identity

The exact key name should be validated during the implementation PR review, but
the design intent is an entity-level `persistence_id` pointer, not a global
heuristic change.

Do not add `CanonicalField.identity_role` or an `IdentityRole` enum in the first
Phase 3 implementation. The canonical model already has `is_id=True`, which is
enough for the bounded `persistence_id` override. Field-level identity roles
remain future work for later business-key, event-id, foreign-key, and
idempotency semantics.

## Translation Contract

The later A1 implementation should modify translation, not Java emitters.

Expected flow:

1. Load optional identity override metadata from the manifest.
2. When selecting an ID for an entity, check whether that entity declares
   `persistence_id`.
3. Validate that the named field exists on the canonical entity.
4. Select that field as the ID and mark the corresponding `CanonicalField` with
   `is_id=True`.
5. Preserve current request-owned ID and `server_generated_id` behavior.
6. If an override is present, bypass the heuristic entirely, including any
   ambiguous-inference warning that the heuristic would otherwise emit.
7. If no override exists, use the current heuristic unchanged.

Generated Java should continue reading `CanonicalField.is_id`; emitters should
not reimplement identity selection logic.

## Interactions

### Server-Generated UUIDs

A1 does not change UUID behavior. `server_generated_id` remains the switch that
decides whether a string persistence ID gets `@GeneratedValue(strategy =
GenerationType.UUID)`. A1 only decides which field is the ID.

### Request-Owned IDs

The existing logic that detects a create-request mapping for the selected ID
field remains valid. If the explicit `persistence_id` appears in the create
request body, the ID is client-supplied. If it does not, current server-generated
behavior applies.

### Cross-Entity Rules

`cross-entity-exists` remains the Phase 3 FK mechanism. A1 may help avoid
mistakenly selecting a foreign key like `accountId` as the entity `@Id`, but it
does not replace the FK rule system in the first implementation.

### Read-Only And Preserved Read Operations

Read-only entities still need persistence identity semantics for generated
single-resource routes and repository lookups. A1 applies to both writable and
read-only CRUD entities.

### B7 And Future Filtered Queries

B7 added per-operation pagination. A future filtered query design may use
foreign-key-like fields as filter dimensions, for example
`listPostingsByAccount(accountId, pageable)`. A1 should not implement filtered
queries, but it helps prevent FK fields from being confused with persistence
identity fields.

### Studio

Studio support is future work. When Studio begins manifest-v1.1 wizard
expansion, it should consider Save/Open Project support as a near-term
prerequisite so identity decisions are not lost between authoring sessions.
Initial Engine design and docs do not require a Studio UI change.

## Generic Example

An e-commerce event ingestion app may model an `OrderEvent` with:

- `orderEventId` as the persistence identity for the generated app
- `orderId` as a foreign key or business reference to an order
- `eventId` as the upstream event bus identifier
- `correlationId` as a workflow trace identifier
- `idempotencyKey` as a replay guard for write handling

The current heuristic might choose `eventId` or `orderId` depending on source
order and naming. The explicit override should let the author declare:

```yaml
identity_overrides:
  - entity: OrderEvent
    persistence_id: orderEventId
```

The generated app then uses `orderEventId` for `@Id`, while the other identifiers
remain regular fields until future role-specific behavior is designed.

## Bounded Implementation Acceptance Criteria

The later A1 implementation PR is ready when it meets all of these:

1. Existing manifests without identity overrides generate identical ID selection
   behavior to the current heuristic.
2. A manifest with multiple identifier-shaped fields can declare
   `persistence_id`, and the declared field wins over the heuristic.
3. If `persistence_id` names a missing field, translation fails with a clear
   deterministic error.
4. `server_generated_id` and request-owned ID behavior remain unchanged after
   the selected field is set.
5. Passthrough-router generation is unaffected.
6. Tests cover at least:
   - explicit override wins on a multi-identifier entity
   - absent override uses existing heuristic behavior
   - missing override field fails clearly
7. The manifest schema/docs describe the optional extension without changing the
   `schema_version: "1.0"` compatibility contract.
8. Duplicate entries for the same entity in `identity_overrides` are rejected at
   manifest validation time before translation.

## Explicitly Out Of Scope

- numeric IDENTITY or SEQUENCE generation
- cursor pagination or filtered query generation
- service-level idempotency behavior
- unique constraints for business keys
- replacing `cross-entity-exists`
- Studio identity-role UI
- passthrough-router identity semantics
