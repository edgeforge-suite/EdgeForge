### MUST-have before intake (2)

#### [Engine] No incremental DB-schema migration: regeneration re-renders V1/V2 CREATE TABLE migrations, breaking already-deployed databases
- **Location:** `appbuilder/generation/sql_emitter.py:emit_sql_files (lines 41,46-59) + _clear_generated_migrations (lines 81-92)`  ·  **Effort:** L  ·  **Dimension:** Product completeness — manifest migration and maintain-over-time gaps
- **What / why it matters:** emit_sql_files always deletes prior EdgeForge-generated Flyway files (_clear_generated_migrations globs 'V*__create_*_table.sql' and unlinks them) and re-emits a fresh sequence of V{index}__create_<entity>_table.sql CREATE TABLE migrations from scratch on every run. There is no ALTER TABLE / incremental migration emission. When a manifest evolves additively over time (e.g. a field added to an existing CRUD entity, or an entity reordered so its V-number shifts), regeneration rewrites the SAME version file (e.g. V1__create_account_table.sql) with new content. An enterprise deployment whose Postgres has already applied V1 will hit a Flyway checksum mismatch on startup (Flyway refuses to boot) or, at best, never apply the new column because the version is already recorded as applied. The generated README even tells teams 'do not change ... migrations for existing tables' (build_emitter.py:780-783) yet the generator itself rewrites them. There is no generated mechanism to evolve a live schema.
- **Why it is new (not already covered):** Not in G7/G8/G10 (those cover import-readiness/security/compliance, not generated-app schema evolution). Distinct from tracker 'staging-prod-hardening' (that row is about staging/handoff-table run-identity/restart/idempotency, not entity-table DDL evolution via Flyway checksum) and from 'gap-evolution-mode' (a Studio-side reopen/BRD-impact-analysis design, not the Engine's generated Flyway emission). Not covered by the multi-session design (that is Studio isolation, not generated-app DB migration).

#### [Engine] Regeneration unconditionally overwrites the service/domain layer where teams are told to add business logic; manual re-apply is the only preservation path
- **Location:** `appbuilder/generation/build_emitter.py:765-786 (section 9 'Where to add business logic') + appbuilder/generation/java_emitter.py:679 ({entity}Service.java) + appbuilder/generation/engine.py:299-306 (_write_file_map)`  ·  **Effort:** L  ·  **Dimension:** Product completeness — manifest migration and maintain-over-time gaps
- **What / why it matters:** The generated agent-context/README directs teams to extend the service and domain layers ('the canonical core', build_emitter.py:772-779), but the Java emitter emits {entity.name}Service.java (java_emitter.py:679) and the domain classes unconditionally, and _write_file_map (engine.py:299-306) does a plain path.write_text for every file with no skip-if-exists, no merge, and no user-owned-file marker. The only output-side exists() checks in java_emitter.py are for INPUT spec/WSDL/manifest paths, never for output files. The README's own guidance (build_emitter.py:784-786) concedes generated files 'are overwritten on regeneration; keep new business logic in clearly separated classes/methods so it is easy to re-apply' — i.e. the maintain-over-time story for hand-added logic is purely manual re-application. For an enterprise team maintaining a generated app across additive manifest changes, every regenerate destroys local edits to the very layer they were told to extend.
- **Why it is new (not already covered):** Not in G7/G8/G10. Distinct from tracker 'studio-reimport-package' (that is Studio reconstructing a manifest from an exported package to re-author, not preservation of hand-edits in the GENERATED Java tree across Engine regen) and 'gap-evolution-mode' (Studio reopen/impact-analysis design). The multi-session design covers Studio per-session isolation and disabling Build-and-Run on shared, not generated-app code-preservation semantics.

### SHOULD-have (19)

#### [cross-repo] Engine MCP allowed-root fails open (and Studio passes the Engine repo as an allowed root), so an unset env var lets any session write into the shared Engine tree
- **Location:** `appbuilder/mcp/tools/generation.py:127-146 (_allowed_roots / _repo_root) and :109-124 (_resolve_allowed_path)`  ·  **Effort:** S  ·  **Dimension:** Multi-tenancy and resource isolation — Engine/KS internals and cross-repo boundaries
- **What / why it matters:** generate_app/validate_manifest/translate_project all gate paths through _resolve_allowed_path -> _allowed_roots(). When EDGEFORGE_MCP_ALLOWED_ROOTS is unset/empty, _allowed_roots() falls back to [Path.cwd(), _repo_root()], where _repo_root() = Path(__file__).resolve().parents[3] — the Engine's own installed package/repo directory. In a SHARED deployment the Engine is a single install shared by every session, so this fallback root is a process-global, cross-session-shared directory. If Studio (or any caller) ever invokes the Engine MCP without setting the env var, a session can resolve manifest_path/output_dir INSIDE the shared Engine install and write generated output there (engine.py mkdirs+writes into output_dir), corrupting the shared tool or planting files another session reads. The CWD fallback is also process-wide. The guard is sound only when the env var is always set to per-session server-owned roots; the unsafe default is the gap. **Cross-repo (post-review):** Studio's `_mcp_env` always passes `str(repo)` as an allowed root (`Studio: app/integrations/appbuilder_integration.py:469`), so the Engine tree is resolvable even when Studio sets roots — the complete fix is two-sided: Engine fail-closed (drop the cwd/repo-root fallback) + Studio passes only per-session workspace roots.
- **Why it is new (not already covered):** Distinct from the multi-session design §5.5/P4: that design flags the Studio *CLI fallback* (_env_with_repo, appbuilder_integration.py) as not root-constrained and says 'prefer the root-constrained MCP path' (lines 249-253). It treats the MCP path as the safe one. This finding is INSIDE the Engine MCP itself: its own _allowed_roots() default includes the shared repo root, so the 'root-constrained MCP path' is only constrained when the env var is set — a fail-open default the design did not examine. Not in G7/G8/G10 (those cover secrets/SBOM/XXE/SSRF, not MCP root-resolution defaults) and not a tracker row.

#### [generated-apps] Generated-app file/XML ingest+output base directories default to /tmp/<bounded_context>/... keyed only on bounded_context — co-located instances of the same (or unnamed) context collide and cross-read each other's data
- **Location:** `appbuilder/generation/java_emitter.py:9932 (app.file-ingest.base-dir), :10502 (app.xml-ingest.base-dir), :10855 (app.xml-output.base-dir); segment from _safe_property_segment(metadata.bounded_context, "app") at :11328`  ·  **Effort:** M  ·  **Dimension:** Multi-tenancy and resource isolation — Engine/KS internals and cross-repo boundaries
- **What / why it matters:** Three emitted base directories default under /tmp/<seg>/ — file ingest (`app.file-ingest.base-dir`), XML ingest (`app.xml-ingest.base-dir`), and XML output (`app.xml-output.base-dir`) — where <seg> = _safe_property_segment(metadata.bounded_context, 'app'), derived ONLY from the manifest bounded_context with no per-instance, per-tenant, or per-run uniqueness (and falling back to the literal 'app' when bounded_context sanitizes to empty). In a shared multi-tenant deployment where two tenants run apps generated from the same bounded_context (or both fall back to 'app'), or co-located apps/replicas share a host or a mounted volume, they resolve the SAME /tmp/<seg>/ingest, /tmp/<seg>/xml-ingest and /tmp/<seg>/xml-output directories. The ingestion controllers read whatever files are placed in the shared ingest dir (baseDir = Path.of(ingestBaseDir)), so tenant A's app can consume tenant B's inbound files, and the shared XML-output dir can be observed/overwritten across tenants. Inner temp filenames are uniqued (UUID.randomUUID(), .tmp-<jobExecutionId>) but the shared base *directory* and final non-temp filenames are not. **Scope (corrected per review):** this is the file-ingest / XML-ingest / XML-output surface only — downstream fixed-width/CSV file output uses a different, non-/tmp path (`./<bounded_context>-eod`) and is **not** part of this collision; the ingest controllers are triggered, not polling. No deployment descriptor or doc recommends a per-instance override (no base-dir override in build_emitter.py; no base-dir guidance in the G7/G8 docs).
- **Why it is new (not already covered):** Not the 'staging-prod-hardening' tracker row (that is DB staging-table run-identity/restart/idempotency, not the /tmp file-ingest base dir) nor any sec-* row. Not G8 (the boundary map covers SOAP SAAJ, operator console, OpenAPI SSRF, credentials — never the filesystem base-dir defaults). Not the multi-session design, which is explicitly Studio-orchestration-scoped and treats generated apps as opaque standalone runtime artifacts; it never examines the generated app's own runtime filesystem-isolation defaults. The operator-console-exposure tracker row is a different surface (HTTP demo endpoints), not shared /tmp paths.

#### [generated-apps] JPA auditor falls back to literal "system" for all writes whenever security is off — which is the only shipped state — so audit columns never record a real principal
- **Location:** `appbuilder/generation/audit_emitter.py:60-67 and :92-93 (return () -> Optional.of("system") when emit_security is False)`  ·  **Effort:** S  ·  **Dimension:** AuthN/authZ/RBAC/audit — beyond the designed Studio seam
- **What / why it matters:** AuditConfig emits an AuditorAware that resolves to SecurityContextHolder's authenticated name ONLY when emit_security is True; otherwise it returns the literal "system" for every CreatedBy/LastModifiedBy column, with a code comment acknowledging this. Since no shipped target profile sets emit_security=True (see catalog finding), the auditor is ALWAYS the constant "system" in practice. So the JPA auditing feature — which exists specifically to attribute row changes to a user — records no real identity in any generated app. For a shared multi-user deployment this means the database-level change-attribution audit trail is uniformly "system" and provides no accountability. The audit scaffolding is effectively inert given the security flag is never enabled.
- **Why it is new (not already covered):** No tracker row covers the audit-attribution behavior; data-governance-posture mentions log PII redaction and Evidence Trail, not JPA created_by/modified_by attribution. This is a direct consequence of the emit_security-never-True fact but is a separate observable gap (audit columns, not access control) and is not in G7/G8/G10 or the Studio design.

#### [Engine] Unescaped allowed-values embedded into generated Java string literals (code injection into generated source)
- **Location:** `appbuilder/generation/java_emitter.py:3417 (allowed_values = ", ".join(f'"{value}"' for value in rule.values))`  ·  **Effort:** S  ·  **Dimension:** Security loopholes — Engine + KS + generated apps
- **What / why it matters:** When emitting the `ALLOWED_<FIELD>_VALUES` Set<String> constant, each allowed value is wrapped with a bare f-string `f'"{value}"'` with NO escaping, producing `private static final Set<String> ALLOWED_X_VALUES = Set.of("v1", "v2");`. `rule.values` originate from `allowed-values` lists in externally-authored rules YAML (appbuilder/rules/ingestion.py:32 / :228 — `values=[str(value) for value in allowed_values]`, no content validation). A value containing a double-quote, backslash, or newline breaks the literal; a crafted value such as `"); } static { /* injected */ } //` injects arbitrary Java into the generated class. This is inconsistent with the SAME file's hardened sink at line 3213, which correctly routes identical `rule.values` through `_java_code_string_literal(value)` (escapes \ " \n \r \t, java_emitter.py:3016). In a shared multi-user deployment, multiple authors supply rules packs; this lets a manifest/rules author inject code into the deterministically-generated artifact rather than only declaring data.
- **Why it is new (not already covered):** Not in G7/G8/G10 (which cover SBOM/secret-scan/SQL-in-KS, not Engine emitter escaping) nor the Studio multi-session design (path/identity/quotas, not generator output sanitization). No tracker row covers it: sec-* rows are SOAP/XML/SSRF/console; A6 is generated-app credential fallback. This is a concrete unescaped-literal sink distinct from the (already-hardened) sibling at line 3213.

#### [Engine] @Pattern(regexp=...) emits OpenAPI/contract pattern via a helper that does not escape newlines or control characters
- **Location:** `appbuilder/generation/java_emitter.py:2739 (@Pattern(regexp="{_java_string_literal(field.pattern)}")) + _java_string_literal at java_emitter.py:2756`  ·  **Effort:** S  ·  **Dimension:** Security loopholes — Engine + KS + generated apps
- **What / why it matters:** `_java_string_literal` (line 2756) escapes ONLY backslash and double-quote: `value.replace("\\", "\\\\").replace('"', '\\"')`. It does NOT escape newlines, carriage returns, tabs, or other control characters — unlike `_java_code_string_literal` (line 3016) used everywhere else. At line 2739 it wraps `field.pattern`, which is taken verbatim from an OpenAPI spec's `schema.get("pattern")` (appbuilder/ingestion/openapi_classifier.py:300) — fully untrusted external input. A pattern containing a literal newline produces a Java source line that splits mid-string-literal (a compile error at minimum), and combined with the rules/contract path provides a content-injection surface into the generated entity/DTO source. The correct, already-present fix is to use `_java_code_string_literal` here too.
- **Why it is new (not already covered):** Distinct from the SOAP/XML hardening tracker rows (sec-soap-saaj, sec-defusedxml) which concern XML *parsing* defenses, not Java emitter escaping. Not in G7/G8/G10 or the Studio design. It is a separate sink/helper from finding #1 (different helper `_java_string_literal`, different annotation, source = OpenAPI spec rather than rules YAML).

#### [Engine] field default_value interpolated into generated Flyway DDL without SQL-literal escaping
- **Location:** `appbuilder/generation/sql_emitter.py:264 (_sql_literal: return f"'{field.default_value or ''}'") used at sql_emitter.py:198 (DEFAULT {_sql_literal(field)})`  ·  **Effort:** S  ·  **Dimension:** Security loopholes — Engine + KS + generated apps
- **What / why it matters:** `_sql_literal` wraps a string default as `'{field.default_value}'` with NO single-quote escaping, and for integer/decimal types interpolates `field.default_value or "0"` raw into the DDL. `default_value` comes from `RuleType.DEFAULT` rules (appbuilder/metadata/translation.py:3002 `accumulator.default_value = rule.value`), authored in external rules packs with no content validation (rules/models.py:37 `value: Optional[str] = None`). The result is written into a Flyway migration (`DEFAULT '...'` in CREATE TABLE) at sql_emitter.py:198 and executed at the generated app's startup. A string default containing a single quote breaks out of the literal; a numeric-typed default carrying `0); DROP TABLE x; --` is interpolated verbatim. This is unescaped, externally-sourced data flowing into generated SQL DDL.
- **Why it is new (not already covered):** G8 verified SQL in KS (parameterized SQLite queries), not Engine's generated Flyway DDL — different repo, different sink. No tracker row addresses DDL emission escaping (sec-* rows are XML/SOAP/SSRF/console). Not covered by the Studio multi-session design or A6. Distinct from findings #1/#2 (SQL emitter, not Java emitter; DDL literal, not Java literal).

#### [Engine] Author's absolute manifest path is embedded verbatim into every generated file header and AuditConfig
- **Location:** `appbuilder/generation/audit.py:render_generated_file_header (the `Source manifest: {source_manifest}` line); fed by appbuilder/cli.py:105 `source_manifest=str(Path(args.manifest))` and appbuilder/mcp/tools/generation.py:69 `source_manifest=str(resolved_manifest)``  ·  **Effort:** S  ·  **Dimension:** Data governance — suite-wide concrete gaps
- **What / why it matters:** Every emitted file (Java sources, pom.xml, application.yml, AuditConfig.java, README) gets a standard header `// Source manifest: <source_manifest>`. Both entry points set `source_manifest` to the *resolved* manifest path: the CLI uses `str(Path(args.manifest))` and the MCP tool uses `str(resolved_manifest)` where `_resolve_allowed_file` returns an absolute path. When an author passes an absolute path (or the server resolves one), that full host path — which can contain a username or an internal project directory name (e.g. `<user-home>/<sensitive-project>/...`) — is baked into generated source that is then committed and shipped downstream. There is no normalization to a basename or a stable logical name. In a shared multi-user deployment this leaks one user's (or the build server's) internal filesystem layout into artifacts handed to other teams.
- **Why it is new (not already covered):** G7 §5 only asserts the *Evidence Trail* carries no PII and G8 treats the manifest as author-trusted design-time input; neither names the generated-file header. The data-governance-posture row scopes generated-app concerns to 'log PII-redaction posture' (runtime logs) and 'Evidence Trail as an audit artifact' — not the path string the Engine writes into every committed source file at generation time. Not an A6/SSRF/SAAJ tracker row.

#### [Engine] Engine generation writes output non-atomically with no cleanup-on-failure — a failed run leaves a half-written, non-buildable app tree
- **Location:** `appbuilder/generation/engine.py:_write_file_map (line 299) and _generate_crud_application (lines 152-217)`  ·  **Effort:** M  ·  **Dimension:** Reliability / ops / observability of the SUITE tools (Engine + KS)
- **What / why it matters:** generate_application runs emitters sequentially (emit_build_files, then emit_java_sources, emit_security_sources, emit_sql_files, demo UI, harness) and each writes files directly into output_dir via _write_file_map (path.write_text in place). There is no temp-dir-then-atomic-rename and no try/except cleanup. If any later emitter raises (e.g. the ~12k-line java_emitter throws on a degenerate manifest, or the process is killed/OOMs mid-run), the output directory is left containing a partial, inconsistent, non-compilable Spring Boot tree. The MCP wrapper generate_app (mcp/tools/generation.py:64-78) catches the exception and returns success=False, but the half-written files remain on disk and pre-existing contents of a reused output dir are silently overwritten with no rollback. Ironically the GENERATED apps emit atomic-move + rollback logic (tests/unit/test_generation.py:2195,6833), but the generator that produces them does not protect its own output. For a shared deployment where many users trigger generations into server-owned dirs, this yields silent corrupt artifacts that look present but are broken. Fix: generate into a temp dir and os.replace/rename on success, or delete partial output on failure.
- **Why it is new (not already covered):** Distinct from the multi-session design's engine.py:299 reference: that design only adds a per-output-path lock + unique output dir to stop CONCURRENT same-path writes from overwriting each other (design §(c), 'concurrent same-path writes overwrite'). It explicitly does not address single-run partial-write / crash-consistency (no temp+rename, no cleanup-on-failure). Not in G7/G8/G10. Not a tracker row (gen-cleanup-bundle is generation-QUALITY of emitted code, not write-atomicity of the generation step).

#### [cross-repo] No structured logging or operational audit trail in the Engine or KS stdio servers
- **Location:** `appbuilder/mcp_server.py (whole file), appbuilder/mcp/tools/generation.py:generate_app, KS: knowledge_server/server.py (all @mcp.tool wrappers)`  ·  **Effort:** M  ·  **Dimension:** Reliability / ops / observability of the SUITE tools (Engine + KS)
- **What / why it matters:** grep for `import logging`/`getLogger`/`logger.` across appbuilder/ returns only Java template strings (kafka_emitter, java_emitter) and zero hits across knowledge_server/. Neither stdio server logs anything: no record of which tool was called, by which project_id, with what args, success/failure, duration, or the exception text on failure. generate_app swallows every exception into an errors=[str(exc)] field with no log line and no stack trace; the Engine CLI only prints human-readable lines to stdout/stderr (cli.py:82,109). In a shared multi-user deployment this means there is no server-side operational log to diagnose a failed/slow generation or ingestion, no audit of who ingested/purged which document on the KS side, and no way to correlate a Studio session failure with the underlying tool call. Fix: add structured (JSON) logging to stderr for tool entry/exit/error with project_id + duration in both servers.
- **Why it is new (not already covered):** Distinct from tracker QG-B6 (MDC/structured logging in the GENERATED CRUD lane — that is the emitted Spring app's logback config, not the Engine/KS Python tools). Distinct from G8 security-boundary-map (boundaries, not runtime telemetry) and the multi-session design (which adds Studio-side audit/ownership hooks and logging in appbuilder_integration._run_subprocess, i.e. the orchestrator, not the Engine/KS servers themselves). The Engine/KS processes are observability blind spots.

#### [KS] KS opens the SQLite index with no integrity/corruption handling — a corrupt or locked DB surfaces as an opaque crash with no recovery or readable error
- **Location:** `KS: knowledge_server/storage/database.py:KnowledgeStore.__init__ (lines 49-55) and server.py:_store (lines 46-48)`  ·  **Effort:** M  ·  **Dimension:** Reliability / ops / observability of the SUITE tools (Engine + KS)
- **What / why it matters:** KnowledgeStore.__init__ does sqlite3.connect(db_path) then immediately PRAGMA journal_mode=WAL and _initialize() (DDL) with no try/except. If the index .sqlite3 file is corrupt, truncated by a crash mid-write, or held by another writer, the very first PRAGMA/connect raises a raw sqlite3.DatabaseError/OperationalError that propagates uncaught out of every tool (_store is called at the top of all 16 @mcp.tool wrappers in server.py). There is no PRAGMA integrity_check/quick_check on open, no detection of a corrupt DB, no rebuild/quarantine path, and no readable diagnostic — the only sqlite error handling in the whole storage layer is the narrow OperationalError catch inside _scrub_sqlite_storage_after_purge (line 907). For a shared deployment, an unclean shutdown or disk-full event that corrupts the FTS5/WAL leaves KS hard-down for that session with an inscrutable stack trace and no recovery story (the index can in principle be rebuilt by re-ingesting sources, but nothing detects corruption or guides that).
- **Why it is new (not already covered):** Not in G7/G8/G10. Not in the multi-session design (which covers per-session KS DB isolation, KS-DB-size quota, idle-reap — all about lifecycle/placement, not corruption detection or recovery of the index file). Distinct from ks-hard-purge/ks-parser-limits tracker rows (erasure + decompression-bomb input guards, not DB-open integrity).

#### [KS] KS runs full schema DDL + table migrations on every single MCP tool invocation (new connection per call)
- **Location:** `KS: knowledge_server/server.py:_store (lines 46-48) and database.py:_initialize / _ensure_suggestion_table / _ensure_manifest_suggestion_review_state_table (lines 60-219)`  ·  **Effort:** M  ·  **Dimension:** Reliability / ops / observability of the SUITE tools (Engine + KS)
- **What / why it matters:** Every one of the 16 @mcp.tool wrappers opens a fresh KnowledgeStore (a new sqlite3 connection) and closes it in a finally block. KnowledgeStore.__init__ unconditionally calls _initialize(), which runs executescript with CREATE TABLE/CREATE VIRTUAL TABLE IF NOT EXISTS, then _ensure_field_catalog_metadata_column (PRAGMA table_info + conditional ALTER TABLE), _ensure_suggestion_table (table-existence checks, possible ALTER TABLE ... RENAME, CREATE INDEX), and _ensure_purge_scrub_pending_table — on EVERY call, including read-only search/list/evidence calls. Beyond the per-call cost (repeated PRAGMA/DDL on the hot path of search), the migration branch in _ensure_suggestion_table can RAISE RuntimeError('Cannot migrate ... both ... contain data') at line 139 from inside a plain search tool, meaning a read query can fail on a schema-migration error path. There is no connection reuse and no separation of one-time migration from per-request open. Under shared multi-user load this multiplies lock contention on the per-session DB and makes every tool call pay (and risk) the migration path.
- **Why it is new (not already covered):** Not covered by any source. The multi-session design addresses WHERE the KS DB lives (per-session path under workspace_root) and its size quota, but not the per-call connect+DDL design of KnowledgeStore. Distinct from all KS tracker rows (ks-hard-purge, ks-parser-limits) which are about data erasure and input parsing limits, not connection/migration lifecycle.

#### [KS] KS purge VACUUM/WAL-truncate scrub has no durable retry — storage scrub can be left permanently pending across process restarts with only an in-DB flag
- **Location:** `KS: knowledge_server/storage/database.py:_scrub_sqlite_storage_after_purge (lines 880-916) and purge_document (lines 790-878)`  ·  **Effort:** M  ·  **Dimension:** Reliability / ops / observability of the SUITE tools (Engine + KS)
- **What / why it matters:** On hard purge, after deleting rows the code attempts up to 4 wal_checkpoint(TRUNCATE)+VACUUM passes with a 50ms busy_timeout and time.sleep(0.05) between tries. If another connection holds the WAL (the design opens a new connection per call, and a shared deployment may have concurrent readers/writers on the per-session DB), the scrub gives up and records a purge_scrub_pending row, returning success=False with a warning telling the operator to 'Close open SQLite readers and retry'. But nothing ever automatically retries the scrub: it is only re-attempted if a human calls purge_document again for the same already-gone document_id (lines 810-832). There is no background sweep, no startup reconciliation that drains purge_scrub_pending, and no logging. For a right-to-erasure/data-governance posture in a shared deployment, purged source-document bytes can remain recoverable in the SQLite freelist/WAL indefinitely while the only record of the incomplete scrub is a silent table row no operator is watching. Fix: drain purge_scrub_pending on store open and/or surface it via the health tool + structured log.
- **Why it is new (not already covered):** Distinct from ks-hard-purge (DONE) which delivered the logical hard-delete/purge PATH and the confirm_purge gate; this is the durability/recovery gap in the physical-scrub RETRY mechanism that purge introduced, which no source tracks. Not in G7 compliance doc (posture statement, not the retry mechanism), not in the multi-session design.

#### [Engine] Generated apps record no manifest schema_version, so there is no provenance signal to drive an upgrade when the schema evolves
- **Location:** `appbuilder/generation/audit.py:render_generated_file_header (lines 6-33) + build_emitter.py:790-794 (section 10 Provenance)`  ·  **Effort:** S  ·  **Dimension:** Product completeness — manifest migration and maintain-over-time gaps
- **What / why it matters:** Every generated file header and the README section 10 Provenance block records source_manifest (a path string), target_profile, and generation_run_id — but never the manifest schema_version it was generated from. The Engine itself pins SUPPORTED_MANIFEST_SCHEMA_VERSIONS = {'1.0'} (core/manifest_versions.py:7) and the docs explicitly anticipate a future additive schema_version '1.1'/'1.x' (manifest-schema.md:420-427). When that evolution lands, there is no recorded marker in any previously generated app telling a maintainer which schema version it was built against, so an enterprise fleet of generated apps cannot be triaged for 'which apps predate feature X / need regeneration'. The provenance that exists is insufficient to support a maintain-over-time upgrade decision.
- **Why it is new (not already covered):** Not in G7/G8/G10 (those are about import-readiness/SBOM/security-boundary, not generated-app version provenance). Not a tracker row — 'manifest-additive-candidates'/'manifest-v2-redesign' cover the schema's own evolution, not embedding the schema_version into generated artifacts for fleet upgrade triage. The C1 agent-context emitter (done-C1-agent-context) is delivered but, as read here, omits schema_version.

#### [Studio] Studio project-snapshot migration chain has a dead step: v1.1->v1.2 jumps the version straight to 1.3, bypassing the explicit v1.2->v1.3 migration
- **Location:** `Studio: app/services/project_file_service.py:deserialize_project (lines 308-318) + _migrate_v1_1_to_v1_2 (lines 348-360) + _migrate_v1_2_to_v1_3 (lines 363-374)`  ·  **Effort:** S  ·  **Dimension:** Product completeness — manifest migration and maintain-over-time gaps
- **What / why it matters:** deserialize_project runs an ordered migration chain on the durable Studio project file. _migrate_v1_1_to_v1_2 sets studio_project_schema_version = STUDIO_PROJECT_SCHEMA_VERSION, and that constant is '1.3' (models/project.py:15), NOT the literal '1.2'. So when a v1.1 file is loaded: line 308 runs _migrate_v1_1_to_v1_2 (version now '1.3'), line 310 re-reads schema_version as '1.3', then line 312 'if schema_version == "1.2"' is False — so _migrate_v1_2_to_v1_3 is skipped entirely for any v1.1 input. Today this is masked because StudioProject pydantic defaults (project_revision=1, created_at=None, etc., models/project.py:652-657) happen to match what the skipped migration would set. But the chain is structurally broken: the moment v1.2->v1.3 (or a future step) needs a non-default transformation, files coming via the v1.1 path will silently skip it and load with wrong/missing data. This is exactly the kind of latent migration bug that surfaces only after a real enterprise upgrade.
- **Why it is new (not already covered):** Not in G7/G8/G10. The multi-session design (PR #200) covers SessionStore catalog/identity/locking but not the project-snapshot version-migration chain correctness. Not 'SS-studio-project-schema' (planned shared-specs schema) and not 'studio-reimport-package'. This is a concrete code defect in the existing save/open migration logic, distinct from any planned design row.

#### [Engine] Actuator health endpoint emits show-details: always to unauthenticated callers (internal infra leak)
- **Location:** `appbuilder/generation/build_emitter.py:920-921 (_render_application_yaml) and :1110-1111 (_render_passthrough_application_yaml); appbuilder/generation/kafka_build_emitter.py:231-232 (_render_application_yaml)`  ·  **Effort:** S  ·  **Dimension:** Generated-app production-readiness (standalone Spring Boot output)
- **What / why it matters:** All three application.yaml generators emit `management.endpoint.health.show-details: always`. Combined with SecurityConfig.java permitAll() on /actuator/health (security_emitter.py:59) — and with security off entirely for every shipped profile — the full health detail (datasource/Hibernate connection state, disk-space free/total, Flyway migration state, broker/Kafka liveness) is returned to any anonymous caller. On a shared multi-user host this discloses backing-store topology and capacity to anyone who can hit the port. Production-safe default is `when-authorized` (or `never`), not `always`.
- **Why it is new (not already covered):** Not in the quality-gate register (Security & Secrets section covers TLS ownership and not-hard-coding secrets, B5 covers probe split, B7/A6 cover credential fallback — none mention actuator detail exposure). Not in G8 security-boundary-map (that maps the suite tools' boundaries, not generated-app actuator config) nor the multi-session design. Distinct from sec-console-exposure-guidance (test console UX), not actuator health detail.

#### [Engine] Generated Dockerfiles run the app as root (no non-root USER, no hardening)
- **Location:** `appbuilder/generation/build_emitter.py:290-322 (_render_dockerfile) and :308-318 (passthrough Dockerfile path); appbuilder/generation/kafka_build_emitter.py:239-268 (_render_dockerfile)`  ·  **Effort:** S  ·  **Dimension:** Generated-app production-readiness (standalone Spring Boot output)
- **What / why it matters:** Both Dockerfile generators produce a runtime stage `FROM eclipse-temurin:{java}-jre` with WORKDIR /app, COPY jar, EXPOSE 8080, HEALTHCHECK, and ENTRYPOINT java -jar — but no `USER` directive, no `groupadd`/`useradd`, no read-only filesystem hint, and no dropped capabilities. The container runs as UID 0. On a shared cluster this fails common Pod Security Standards (`runAsNonRoot`), maximizes blast radius of any RCE, and is rejected outright by many enterprise admission controllers. Adding a non-root user line is a one-line hardening.
- **Why it is new (not already covered):** Container/Dockerfile hardening is not covered anywhere: E7 in the register is about optional K8s/Grafana/ELK deployment hooks (deployer-owned), not the emitted Dockerfile's user. G7/G8/G10 are Engine-repo import-readiness and never inspect generated Dockerfile contents; the multi-session design is Studio-process isolation, not generated-image hardening.

#### [Engine] No graceful shutdown configured in generated apps — in-flight requests/Kafka work dropped on rolling deploy
- **Location:** `appbuilder/generation/build_emitter.py:831-925 (_render_application_yaml — server: block only sets port: 8080); same omission at :1087-1114 (passthrough) and kafka_build_emitter.py:_render_application_yaml`  ·  **Effort:** S  ·  **Dimension:** Generated-app production-readiness (standalone Spring Boot output)
- **What / why it matters:** The emitted application.yaml `server:` block contains only `port: 8080`. There is no `server.shutdown: graceful` and no `spring.lifecycle.timeout-per-shutdown-phase`. Spring Boot defaults to immediate shutdown, so on the rolling restarts and pod evictions that are routine in a shared multi-user cluster, in-flight HTTP requests are terminated mid-transaction and (for the Kafka archetype) in-flight consume/transform/publish work is cut off without draining, increasing duplicate-delivery and partial-commit windows the app otherwise tries to avoid.
- **Why it is new (not already covered):** Not in the register: B5 is specifically the liveness/readiness probe split, not connection draining/shutdown; no other row mentions graceful shutdown. Out of scope items (G7/G8/G10, multi-session, tracker QG-B5) do not cover generated-app shutdown semantics.

#### [Engine] Generated pom.xml pins a frozen Spring Boot baseline (3.3.5) with no dependency-CVE / version-currency gate
- **Location:** `appbuilder/generation/build_emitter.py:230-258 (_render_pom_xml) and :938+ (_render_passthrough_pom_xml); appbuilder/target_profiles/catalog.py:36,52,68 (spring_boot_baseline="3.3.5")`  ·  **Effort:** M  ·  **Dimension:** Generated-app production-readiness (standalone Spring Boot output)
- **What / why it matters:** Every generated pom.xml inherits spring-boot-starter-parent at a single hardcoded baseline of 3.3.5 (an Oct-2024 release) across all three profiles, and the emitted <build> contains only spring-boot-maven-plugin — no OWASP dependency-check, no CycloneDX/SBOM plugin, no versions-maven-plugin, and no Dependabot/renovate descriptor. There is no mechanism in the generated artifact to detect or surface transitive CVEs, and the baseline does not advance as the product ages, so apps generated in 2026 ship a pinned 2024-era dependency tree with no in-repo CVE/dependency scanning and a baseline that does not advance as the product ages (unscanned / stale-baseline risk; specific CVEs are not assessed here). For a shared deployment this means each generated service is a frozen, unscanned dependency surface.
- **Why it is new (not already covered):** G7 (docs/compliance-and-portability.md §6 / handover-evidence sbom.cdx.json) covers the EdgeForge Engine repo's OWN dependency hygiene and SBOM — confirmed at compliance-and-portability.md:148-150 it is regenerated for the suite via make sbom, not for generated-app poms. The generated app's CVE posture and baseline-currency are not covered by G7/G8/G10, the multi-session design, or any tracker row (sec-defusedxml/sec-soap-saaj are specific library rows, not a generated-pom CVE/version-currency gate).

#### [cross-repo] Neither stdio server exposes a usable health/readiness signal that reflects backend state (DB openable / writable)
- **Location:** `docs/engine-mcp-design.md:103-106 (design decision) corroborated by appbuilder/mcp_server.py and KS: knowledge_server/server.py having no health tool`  ·  **Effort:** S  ·  **Dimension:** Reliability / ops / observability of the SUITE tools (Engine + KS)
- **What / why it matters:** The Engine MCP design explicitly states the health check is 'the MCP handshake plus tool discovery' and that Phase 4 'intentionally does not add an HTTP /_health endpoint' (engine-mcp-design.md:103-106). KS has no health/ping tool at all. The handshake-as-health approach only proves the Python process started and can list tools; it does not verify that the KS SQLite index is openable/writable, that disk space exists for generation output, or that allowed-roots are configured correctly. A KS process can pass list_tools yet fail every real call because the DB file is corrupt or the configured EDGEFORGE_KS_DB_PATH dir is unwritable (see the no-integrity-handling finding). For a shared deployment, an orchestrator/operator has no cheap readiness probe to distinguish 'server up but backend broken' from 'server healthy' without running a real (mutating) tool. Fix: add a lightweight read-only health/ping tool to each server that touches the backend (e.g. KS does a trivial SELECT 1 against the DB; Engine confirms allowed-roots + schema availability).
- **Why it is new (not already covered):** Distinct from tracker QG-B5 (split K8s liveness/readiness probes for the GENERATED apps' actuator, not the Engine/KS stdio servers). The engine-mcp-design note documents the decision but the readiness gap for backend state is unaddressed and KS has nothing at all. Not in G7/G8/G10 or the multi-session design.

#### [Engine] Forward-compat asymmetry: the default generate path silently ignores unknown manifest fields while --validate-schema rejects them
- **Location:** `appbuilder/contracts/manifest.py:load_project_definition (line 1186 ProjectDefinition.model_validate) vs appbuilder/cli.py:96-100 (validate_package_or_raise) + appbuilder/schema/manifest-v1.schema.json:7 (additionalProperties false)`  ·  **Effort:** S  ·  **Dimension:** Product completeness — manifest migration and maintain-over-time gaps
- **What / why it matters:** Two different validation paths disagree on unknown fields. The normal `generate` path builds the manifest via ProjectDefinition.model_validate (manifest.py:1186); ProjectDefinition is a plain pydantic BaseModel with no extra='forbid', so unknown/extra top-level keys are silently dropped. The optional `--validate-schema` path (cli.py:96-100 -> validate_package_or_raise -> Draft202012Validator over manifest-v1.schema.json) sets additionalProperties:false at the root, so the same unknown key is rejected. This asymmetry is specifically about **unknown/extra fields under an accepted `schema_version`** (today only `1.0`). A forward `schema_version` bump such as `1.1` is already rejected up front by the version gate `SUPPORTED_MANIFEST_SCHEMA_VERSIONS={'1.0'}` (core/manifest_versions.py:7), so this is **not** a version-bump scenario. The maintain-over-time hazard: when the schema later admits a new optional field under additive (still-`1.0`-compatible) evolution, an older Engine silently accepts-and-strips that field under `generate` (its intent vanishes with no error) but hard-rejects it under `--validate-schema` — so whether the older Engine fails-closed depends on an optional flag most generation flows do not pass.
- **Why it is new (not already covered):** Not in G7/G8/G10. Distinct from 'manifest-additive-candidates'/'manifest-v2-redesign' (those define WHAT may be added, not the dual-path accept/reject inconsistency for an old Engine reading a newer additive manifest). Not in the multi-session design. Grounded in the divergence between the pydantic load path and the JSON-schema validate path I read.
